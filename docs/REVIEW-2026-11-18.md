## 1. The short version

Claude Bridge has the right skeleton: instant send, news back, transcripts as the only record, one
hub per account. The problems are in three places.

**1. Reading is done with the wrong tool.** Today every "what did it say?" goes through
`catch_up`, which runs a model over the whole conversation. Your instinct is right: reading the
last few messages needs no model at all. The transcript already holds everything, including who
sent each message.

- Add **`read_session`**: reads the transcript, no model, whole messages, paged. This answers
  "the last message", "the last three", "what happened since I last looked", and "find the error".
- Make **`catch_up`** only the hand-off tool: "I worked at the computer for hours, now I am on
  the phone, give me the processed picture". It returns a short briefing and the status, not six
  whole exchanges.

**2. Tokens are spent when nobody is listening.** The briefing is rewritten after every watched or
app turn (a full re-read of the conversation each time, about 497,000 tokens here), whether or not
anyone ever calls `catch_up`, and then it is lost on every plugin reload. Make it lazy, stored,
and built from only what is new since the last briefing.

**3. News can be lost, and you would not know.** The relay marks news as "heard" the moment it
writes it into a result. If that result never reaches the Claude app (the failure in incident 2),
the news is gone from the feed. The feed needs a cursor the app confirms.

The ten changes that matter most, in order:

| # | Change | Why |
| --- | --- | --- |
| 1 | News is confirmed, not assumed (cursor + cancel on disconnect) | Nothing is ever missed |
| 2 | Briefing: lazy, stored, built from the new part only | Removes almost all briefing cost |
| 3 | `read_session` (transcript, no model, paged, searchable) | The cheap path you asked for |
| 4 | `catch_up` slimmed to briefing + status | About 80% fewer tokens per call |
| 5 | Exact "typed vs app" from `origin`; skip compaction and interrupt rows | Fixes wrong labels |
| 6 | An inbox model: every session has an "unheard" count | One simple idea replaces three |
| 7 | Old news becomes one line per session, not a dump | No token blast after a day away |
| 8 | Relay permission prompts and "waiting on screen" to the app | Sessions stop stalling silently |
| 9 | Tool list and instructions on a diet (about 4,500 → 2,300 tokens) | Paid in every conversation |
| 10 | Link codes that cannot be stolen by listening; revoke a computer | The code is spoken aloud |

Three bugs found on the way that are worth fixing at once: after `stop_session`, the app's next
message is never sent (4.4.1); a reply can lose its "for the app" mark when the plugin reloads
(4.4.2); a side chat forgets it is a side chat after about 4,096 messages (4.4.3).

## 2. The goal

**What it is for, in your words:** you talk to your Claude Code sessions from the Claude app,
mostly by voice, mostly from the phone. You ask a session to do something, hear when it is done,
answer its questions, start and resume and fork sessions, and move between the computer and the
app in the middle of work without losing the thread.

**What "the best experience ever" means for that.** I wrote these as tests the design must pass:

1. **Nothing is missed.** If a session said it, you can hear it. A dropped connection, a reload
   or a restart never loses a message without a trace.
2. **Nothing is cut.** Every message arrives whole. Long things are paged, never shortened.
3. **The cheap question is cheap.** "What did it just say?" costs the size of the answer and
   nothing more: no model call on the computer, well under a second.
4. **The expensive answer is asked for, never spent by itself.** A model runs over a session
   only when you ask for something that needs one.
5. **Moving is one sentence.** "Catch me up on Nav" gives a 20 to 30 second spoken picture and
   leaves you able to carry on.
6. **A session never waits in silence.** If it is blocked (a question, a permission, a dialog on
   screen), you hear that, and where possible you can answer from the phone.
7. **You always know where things stand.** Which sessions exist, which are working, which have
   said something you have not heard.
8. **It is safe by default.** A leaked code, a tricked assistant or a stolen phone cannot quietly
   run things on your computers.
9. **It costs little to leave on.** Idle time costs nothing, on the computer, at Cloudflare and in
   the Claude app's context.

The rest of this review measures the current design against these nine and proposes the smallest
changes that pass them.

## 3. What works and should stay

- **Instant send, news back.** No tool waits for Claude Code to work. This is the right shape for
  voice and for the app's 240 s limit.
- **Transcripts are the only record.** No database of messages at Cloudflare. Keep this; the new
  reading path leans on it even harder.
- **One Durable Object per account, hibernating WebSockets.** Idle costs nothing; routing is
  simple. Cloudflare's own guidance matches this design.
- **Device, project, session, addressed by name.** No "active session". Good for voice.
- **Real forked sessions for side chats** on the original's model and effort.
- **The HTTP fallback** for Macs that block helper programs, behind the same `Handle`.
- **Signed, stateless OAuth**, account id derived from the key, per-computer credentials.
- **Pause everywhere**, which only a computer can lift.
- **Questions relayed to the app** with a 15-minute window and "answer on screen".
- **Message-to-turn matching by the submit's resolution**, not by text (it needs one hardening,
  4.4.2).
- **Whole messages, batches split not cut** (1.6.0).

## 4. Findings: gaps, bugs and gotchas

Each item has its evidence. Severity: **High** (loses data, wastes a lot, or blocks the main use),
**Medium**, **Low**.

### 4.1 Catching up and reading

**4.1.1 `catch_up` is the only way to read, and it always runs a model. High.**
`catch_up` returns status + briefing + six whole exchanges + files (`plugin/hooks/catchup.ts:83-103`)
and calls `currentBrief`, which makes a new briefing whenever a turn has finished since the last
one (`plugin/hooks/side.ts:123-127`). So "what was the last message?" costs a model call over the
whole conversation (measured 2.5 to 7.8 s; about $0.10 warm, $2.50 to $4.00 cold) plus 4,000 to
5,000 tokens in the Claude app. There is no way to ask for only the last reply, only what changed,
only the status, or older exchanges. Its status repeats `list_sessions`; its last reply repeats
what `wait_for_updates` already delivered.

**4.1.2 The briefing is rewritten after every turn, used or not. High.**
`turn.complete` calls `refreshBrief` for every turn that was for the app or in a watched session
(`plugin/hooks/register.tsx:469`), at most once a minute (`side.ts:117-120`). Each one is a
`$.model.fork`: the whole conversation sent again (`side.ts:98`). A day with 60 such turns on this
session is about 30 million cache-read tokens (about $6 at API prices; on a subscription it eats
the usage limit) for briefings that mostly nobody reads.

**4.1.3 The briefing lives only in memory. High in mod mode, Medium otherwise.**
`rt.brief` is module memory (`plugin/hooks/state.ts`, the `rt` object: "Reset on every load").
In mod mode the plugin reloads when each turn ends (`docs/DECISIONS.md`, 2026-11-18 item 3). So the
briefing made after a turn is thrown away by the reload that follows, and the next `catch_up`
pays for it again. The plugin API has storage that survives a reload (`$.store`, `$.state`).

**4.1.4 "Typed on the computer" vs "sent from the app" is a guess. Medium.**
`catchUp` compares each message's first 400 characters against the last 50 app messages kept in
the panel's log (`catchup.ts:87-88`; the log keeps 50, `state.ts` `addLog`, `.slice(-50)`). After
50 app messages, older ones are labelled "computer". The transcript has the exact answer on every
user row. Measured on the largest Nav transcript (9,578 rows, 30 MB): 58 rows
`origin: {"kind":"human"}`, 26 rows `origin: {"kind":"plugin","name":"codebridge","asUser":true}`,
16 rows from the `voice` plugin, plus `peer` and `task-notification` rows. The plugin API's
`session.append` event carries the same thing live: `door` (`prompt`, `compaction`, `queue`, ...)
and `origin` (`composer`, `bridge`, `plugin` with its name, `peer`, `channel`, ...), with the
row's `uuid` (types file, `SessionAppendInput` and `PromptOrigin`).

**4.1.5 Compaction summaries and interrupt markers are treated as the person's messages. Medium.**
`exchangesOf` accepts any user row with text that does not match one regex
(`catchup.ts:35-41`, `state.ts` `NOT_THE_PERSON`). The compaction summary ("This session is being
continued from a previous conversation…", `isCompactSummary: true`; 2 such rows in the measured
transcript) and "[Request interrupted by user]" pass that test. Messages typed through the `voice`
plugin, Remote Control (`bridge`) and other sessions (`peer`) are all lumped under "computer".

**4.1.6 Every read loads up to 4,096 rows. Low.**
`$.session.messages()` with no arguments returns the newest 4,096 entries; the API says "the more a
read returns the more it costs: `last` or `after` cuts it". It is called unbounded in `catchUp`
(`catchup.ts:86`), at every watched turn's end (`plugin/hooks/claude.ts:143`) and at every plugin
load (`register.tsx:272`).

**4.1.7 A message over about 150,000 characters cannot arrive whole. Low, but it breaks "never cut".**
Claude's connector limit is "~150,000 characters" per tool result (Anthropic's connector docs).
The relay's rule "a single message larger than the budget still goes whole, alone"
(`relay/src/hub.ts:128-132`) would then be cut by the Claude app, not by the bridge. Only paging
inside one message can keep the promise.

**4.1.8 A closed session cannot be read without resuming it. Medium.**
Resuming opens the session and the first turn re-reads its whole context (cold: dollars, not
cents). "What was the last thing in number 3?" should be a file read by the device agent.

### 4.2 News and reliability

**4.2.1 News is marked heard when written, not when received. High.**
`withUpdates` moves the cursor to the newest item as it builds the result
(`hub.ts:1348` and `hub.ts:1393`). Nothing confirms the Claude app got that result. If the HTTP
response is lost (incident 2: "the connector's server isn't responding"), those items are
"heard", stay one more hour, and are never offered again: `pendingUpdates` only returns items past
the cursor (`hub.ts:1303-1308`). The hour of kept news is unreachable by any tool.

**4.2.2 A wait whose caller has gone still eats the news. High.**
`waitForUpdates` holds up to 200 s on a timer (`hub.ts:1207-1237`). The Worker does not listen
for the caller going away (`relay/src/mcp.ts` has no `request.signal`), and it drops every
JSON-RPC notification, including `notifications/cancelled` (`mcp.ts:33` keeps only messages with
an id; `mcp.ts:39` answers 202). Since the compatibility date `2026-10-01`, a pending timer keeps
the object alive with no client connected (Cloudflare changelog). So when the app gives up early,
the hub keeps waiting, news arrives, the hub writes it into a result for nobody, and marks it
heard. This is the most likely way incident 2 lost news. **Not verified** live.

**4.2.3 Incident 2 itself: probable causes, and how to tell. High.**
A 200 s call with not one byte sent is fragile. Candidates:

- an idle timeout between the Claude app's servers and the Worker, or a shorter limit in the
  voice client, on a connection that carries no bytes;
- Cloudflare restarting the isolate (runtime updates happen without a deploy) while the call is
  held; in-memory waiters die with it (`hub.ts:177-188`);
- on the Workers Free plan, the daily duration limit (13,000 GB-s; one object held active all
  day is about 11,000 GB-s). Past it, operations fail until 00:00 UTC. Unlikely here, since the
  relay answered quickly the same day, but worth one look at the dashboard.

Today nothing records which one happened. The relay logs only the tool's name
(`mcp.ts:83`). See 6.3 for a diagnostic log the CLI can read.

**4.2.4 After time away, old news floods in. High for tokens.**
Unheard news waits 7 days (`hub.ts:123`). The first call after a day away returns up to 50,000
characters of old replies (`hub.ts:132`), about 12,500 tokens, then says more are waiting, call
again. That is the opposite of what you described: after a long absence you want the processed
picture (`catch_up`), not a replay.

**4.2.5 Every session's every reply goes to Cloudflare, watched or not. Medium (privacy, storage).**
`turn.complete` sends the `finished` event with the full reply unconditionally
(`register.tsx:462-467`); only `changes` depends on watched or for-app (`register.tsx:442`). The
hub stores it (`hub.ts:1289`) and only filters at delivery (`hub.ts:1298-1300`). Sessions you never
meant to expose have their replies kept at Cloudflare for up to an hour after the cursor passes,
or 7 days if the app is not used.

**4.2.6 Incident 1 is by design, but the design gives no hint. Medium.**
A message typed at the computer in an unwatched session is stored and filtered out. The app has no
way to learn "Nav did two things you have not heard" short of calling `catch_up` on it.

**4.2.7 The feed is read whole on every event and every call. Low now, grows.**
`feed()` lists every `ev:` row (`hub.ts:1311-1322`); `record` calls `pruneFeed`, which lists them
all again (`hub.ts:1290`, `hub.ts:1325-1336`); `withUpdates` and `waitForUpdates` call
`pendingUpdates` up to three times. Cost grows with the square of the backlog.

**4.2.8 An idle wait returns a list each time. Medium for tokens.**
"No news" comes with every watched or working session described in full
(`hub.ts:1229-1234`). Each poll also costs the Claude app a model turn. Twenty idle polls an hour
add several thousand tokens of context for no information.

**4.2.9 The app's own request is repeated back in full. Low to Medium.**
`finished`, `stopped` and `failed` lines quote the whole task (`hub.ts:1357`, `hub.ts:1367`). For
the app's own messages that is text the assistant sent a minute earlier.

**4.2.10 Watching never lapses. Low.**
The watch list is pruned of closed sessions only when `watch_sessions` is called
(`hub.ts:1194`). `waitForUpdates` treats a stale id as something to wait for (`hub.ts:1213`), so
it can hold 180 s for a session that is gone.

**4.2.11 A retried send can go twice. Low.**
The duplicate guard is the same text within 20 s (`claude.ts:31`). If a `send_message` result is
lost and the assistant retries after 20 s, the session gets it twice.

**4.2.12 One stream of news per account. Known.** Two Claude app conversations share a cursor
(decision 15). A confirmed cursor (6.3) makes this safe instead of lossy.

### 4.3 Token waste, summed up

| Where | Today | After |
| --- | --- | --- |
| Briefing after each watched/app turn | ~497k cache-read tokens each (this session) | 0 |
| `catch_up` when the briefing is stale and the cache is cold | $2.50 to $4.00 | about $0.01 to $0.05 |
| "What was the last message?" | a `catch_up`: 4,000 to 5,000 tokens + a model call | the message + ~40 tokens, no model |
| `ask` for an exact quote | a full-context model pass | a text search, no model |
| Tool list + instructions, every conversation | 18,006 characters (~4,500 tokens) | ~9,000 characters (~2,300) |
| Idle `wait_for_updates` | ~100 to 400 tokens | ~10 tokens |
| First call after a day away | up to ~12,500 tokens per call, several calls | one line per session |
| App's own request echoed in news | the whole request again | a short label |

Measured: instructions 4,710 characters (804 words), tool definitions 13,296 characters. The
shared `session`, `device` and `open_in` descriptions are repeated in 8, 10 and 3 tools
(`relay/src/tools.ts:34-48`), and the instructions restate most tool descriptions
(`tools.ts:15-32`).

### 4.4 Plugin correctness

**4.4.1 After `stop_session`, the app's next message is not sent. High. Verify first.**
`turn.complete` sets `rt.stopStands = true` on any abort (`register.tsx:453`), including the one
the app asked for (`claude.ts:173-179`). `sendMessage` then puts every message in the prompt box
and tells the assistant to have you press Enter (`claude.ts:38`). So "stop Nav and have it do X
instead", said from the phone, leaves X sitting on the computer. The rule exists because Claude
Code drops plugin prompts after the *person* interrupts. The plugin API says of a plugin's own
`$.turn.abort`: "no interruption marker" and "the prompt this plugin submits next is the context",
which suggests the app's own stop does not need the rule. **Not verified** live.

**4.4.2 A reply can lose its "for the app" mark. Medium.**
Which messages a turn carries is module memory (`rt.entering`, `rt.turnEntries`,
`state.ts`). A reload between a queued send and its turn (every turn end in mod mode; any plugin
update otherwise) forgets it, and the reply goes out unmarked: unwatched sessions then never
deliver it. The transcript's `origin` on the row that started the turn is the durable answer.

**4.4.3 A long side chat forgets it is one. Low.**
`session.start` looks for the fork note in `$.session.messages()` (`register.tsx:272-275`), which
returns only the newest 4,096 entries. The measured session has 3,649 user and assistant rows; a
little more and the first prompt is out of reach. Keep `isSide` and `parent` in `$.store`.

**4.4.4 Type mismatch near `register.tsx:511`** against Claude Code 2.1.326 (known).

**4.4.5 Diagnostics go to `/tmp`. Low.**
The per-session log (`register.tsx:261`, `state.ts` `note`) holds the first 160 characters of
every app call (`plugin/hooks/connector.ts`, the `pump` function) in a world-readable folder.
macOS gives each user a private `$TMPDIR`.

**4.4.6 Stale comments.** `plugin/hooks/images.ts:3` and `plugin/hooks/inside.ts` (in
`toolResult`) say the relay's limit is 1 MiB; Cloudflare now accepts 32 MiB and the connector
allows 16 MiB (`plugin/connector/connector.swift:236`). `inside.ts` says "the latest 20" where
the code keeps 500.

### 4.5 Relay and Cloudflare

**4.5.1 In-memory state dies with the isolate.** Pending calls, waiters, the names cache, polling
peers and the answer mailbox (`hub.ts:177-188`). A call in flight during a restart fails; its side
effect may already have happened (see 4.2.11).

**4.5.2 HTTP-polling sessions keep the object awake.** One held `POST /peer` at all times
(`hub.ts:604-639`) means duration is billed all day while such a session is open (128 MB × 86,400 s
≈ 11,059 GB-s a day). Inside the paid plan's 400,000 GB-s a month for one account; close to the
Free plan's 13,000 GB-s a day.

**4.5.3 Old accounts and link hubs are never cleaned.** A new key means a new hub; the old one's
storage stays. An expired link offer stays in its hub (`hub.ts:382-410` deletes only on success).

**4.5.4 `POST /link/<code>` is open to anyone** (`relay/src/index.ts:131-137`): each call makes a
Durable Object with storage. No rate limit.

### 4.6 Security and privacy

**4.6.1 The link code can be stolen by anyone who hears it. High for a code that is read aloud.**
The code is the only secret: whoever calls `GET /link/<code>` first after approval gets the
credential (`hub.ts:390-410`, `index.ts:131-137`). You say the code out loud to a voice assistant.
The OAuth device flow (RFC 8628) solves exactly this with two values: a secret the device keeps
and a code the person reads. The computer should send its own secret when it offers the code and
again when it collects; the spoken code alone is then useless.

**4.6.2 A linked computer cannot be removed.** The hub keeps `linked` hashes and checks them
(`hub.ts:196-202`), but nothing deletes one. The roadmap has it; it should ship with 4.6.1.

**4.6.3 What a linked computer can do.** It joins as a peer: it can send events (which the voice
assistant reads out), pause the account, change the watch list, and receive calls addressed to a
session id it claims (a newer connection of the same session replaces the old one,
`hub.ts:571`). So a stolen credential can read messages meant for a session and feed the assistant
false news. Worth saying plainly in the README's safety section.

**4.6.4 The assistant as a confused deputy.** The Claude app may have other connectors. Text from
an email or a web page could tell the assistant to `send_message` something harmful to a session
running in bypass mode. Present defences: the app asks before using a connector tool unless you
chose always-allow; `send_message` is marked not read-only; "Ask me first" per session; news is
labelled as reports. Suggested additions in 6.8.

**4.6.5 No single app can be signed out.** Tokens are signed, not stored; `revoke` does nothing
(`relay/src/oauth.ts:289-291`); a refresh token lasts 90 days. Only a new key cuts access. Fine
for one person; say so.

**4.6.6 The key file is world-readable for a moment.** It is written, then `chmod 600`
(`plugin/hooks/connector.ts`, `bridgeKey`). Create it with the right mode instead.

### 4.7 The voice experience

**4.7.1 A session blocked on a permission prompt is silent. High.**
The README says permission prompts "stay on screen". From the phone, the session just stops
answering. Claude Code has a supported way to forward these: the plugin API exposes the
`PermissionRequest` hook (`classic.PermissionRequest`: tool name, input, allow or deny) and
Channels have a documented permission relay. Remote Control already pushes "actions required" to
the phone.

**4.7.2 Other blocks are invisible too.** Plan approval, trust prompts, MCP consent, a usage
prompt. The assistant cannot tell "working" from "stuck on a dialog".

**4.7.3 "Pass on everything in full" versus listening.** The instructions tell the assistant to
relay each message whole (`tools.ts:28`). A 2,000-word reply is about 13 minutes of speech. That
is your call (open question 3); section 6.7 offers a way to keep "whole" and still be pleasant.

**4.7.4 A Mac that sleeps mid-task goes dark.** A session looks alive for up to 90 s after its
computer sleeps (`hub.ts:118`); then calls time out. Nothing keeps the Mac awake during work the
app started.

**4.7.5 No push.** When no call is waiting, nothing tells the phone a long task finished.
`$.ui.notify` exists for this (title, `key`, `delayMs`, `untilBack`), and reaches a phone when the
session has a host that raises notifications. **Not verified** that it reaches your phone.

### 4.8 Docs that drifted

## 5. What others do, and what the platforms allow

### 5.1 Anthropic's own paths

- **Remote Control** connects claude.ai/code and the Claude mobile app to a session on your
  machine: outbound HTTPS only, the full transcript on the phone, sending from any device,
  forking from the web, and **mobile push** ("Push when Claude decides", "Push when actions
  required" for permission prompts and questions). No voice conversation. It is a view of one
  session, not an assistant across sessions.
- **Channels** (research preview) let an MCP server push messages into a running session
  (Telegram, Discord, iMessage). The reference documents **permission relay**: Claude Code sends
  `permission_request` with a five-letter id, the tool name, a description and an input preview;
  the remote person answers allow or deny; the local dialog stays live and the first answer wins.
  It warns: only do this where the sender is authenticated, and treat the fields as untrusted.
- **Voice mode** (its 2026 update) runs on Opus, Sonnet and Haiku, reaches connected tools, asks
  permission before using one, and "voice conversations count toward regular usage limits". So
  every token the bridge returns is paid for twice: once to produce, once to listen to.
- **Connector limits**: "~150,000 characters" per tool result and "240 seconds per tool call" on
  claude.ai and Desktop. Claude does not support resource subscriptions, sampling, or draft MCP
  features, so the server cannot push; polling with a held call is the only way.

**What this means:** Claude Bridge's own ground is the voice assistant that works across all your
sessions and computers. Remote Control is the better *screen* for one session. They fit together:
the bridge for talking, Remote Control for looking (6.9).

### 5.2 Third parties

Happy (open source: an agent runtime on the computer, a phone app, a relay that "only sees
ciphertext", voice as a paid feature), Omnara (now a platform for running agents), Conductor,
T3 Code, Codex in the ChatGPT app (paired by QR code), and SSH with tmux over Tailscale. All of
them build their own phone app. None rides on the Claude app's own voice assistant. Two ideas
worth borrowing: end-to-end secrecy from the relay (not possible while the Claude app must read
the text, so self-hosting stays the answer), and pairing by QR code with a device-held secret
(4.6.1).

### 5.3 Tool design (Anthropic, "Writing effective tools for agents")

- Fewer, deliberate tools shaped around what people actually ask for.
- "Return only high signal information"; names over ids.
- Let the caller choose detail: their example reply was 206 tokens detailed, 72 concise.
- Pagination, ranges, filtering, with sensible defaults; when there is more, say how to get it.
- Errors that say what to do next.

`read_session` is this advice applied: a range, a filter, a default of one, a cursor for more.

### 5.4 MCP transport facts that matter here

- A server may answer a POST with `text/event-stream` instead of JSON and send notifications
  before the result (Streamable HTTP, spec 2025-11-25). A held call can therefore carry
  keep-alive bytes.
- "Disconnection SHOULD NOT be interpreted as the client cancelling"; the client "SHOULD"
  send a cancellation notification on timeout. The relay should honour both signals.
- A client "MAY" reset its timeout on progress notifications but "SHOULD always enforce a maximum".

### 5.5 Cloudflare facts that matter here

- Free plan: 100,000 requests and 13,000 GB-s a day; past either, operations fail. Paid: 1 million
  requests and 400,000 GB-s a month included.
- Hibernating WebSockets are not billed while idle; automatic ping replies are free.
- From compatibility date 2026-10-01, pending timers and RPCs keep an object alive (and billed)
  up to 15 minutes each with no client connected.
- A code update resets in-memory state; "make operations retryable and persist important state".
- SQLite-backed objects: key + value up to 8 MB; WebSocket messages up to 32 MiB.
- `request.signal` tells a Worker the caller went away (flag `enable_request_signal`). A Workers
  GitHub discussion reports it is not always detected (secondary; not verified), so it helps but
  cannot be the only guard.

### 5.6 Claude Code facts that matter here (from the plugin API types)

- `$.session.messages({ last })` and `({ after: uuid })`: ranged reads, each row with its `uuid`.
- `$.fs.read(path, { offset, length })`: read the tail of a large transcript (up to 4 MiB a read).
- `session.append` hook: every row with `door`, `origin`, `uuid`.
- `$.model.complete({ model, prompt, effort, timeoutMs })`: one completion with **no history**;
  the result carries token `usage`. `$.model.fork` also reports `usage`, including how much the
  cache served, so the plugin can *measure* warm versus cold instead of guessing.
- `$.store` / `$.state`: values that survive a reload.
- `$.ui.notify`: native notification through the person's channel, with `untilBack`.
- `classic.PermissionRequest` hook; `tool.check` (allow, ask, deny).
- `$.session.usage()`: context fill, rate-limit windows, cost.
- The prompt cache: third-party reports say Claude Code keeps the main conversation's cache for
  one hour on a subscription within plan usage and five minutes otherwise; reports disagree on
  dates. Treat the lifetime as unknown and measure it (6.5).

## 6. The proposed architecture

### 6.1 Three planes, each with one job

```
                     Claude app (voice)
                            │  MCP, one POST per call
                ┌───────────┴────────────┐
                │   relay (hub per account)   │
                │   routes, keeps the inbox   │
                └───┬─────────┬─────────┬─────┘
        live news   │  reads  │         │  thinking
   (push, small)    │ (pull,  │         │  (pull, asked for)
                    │ no model)│        │
              plugin: events   plugin: transcript   plugin: briefing, ask
                    └─────────┴─────────┘
                    Claude Code transcript (the only record)
```

| Plane | Question it answers | Cost | Tools |
| --- | --- | --- | --- |
| **Live news** | "What just happened?" | The reply's own size | `wait_for_updates`, news on results |
| **Reads** | "What did it say? Since when? Where is the error?" | The text's size; no model | `read_session`, `list_sessions` |
| **Thinking** | "Give me the picture." "Why did it…?" | A model, only when asked | `catch_up`, `ask` |

Today the first and third planes exist and the second is missing, so the third does the second's
work. Adding the read plane is the heart of this review.

### 6.2 The inbox: one idea for "what have I not heard"

Give every session a **read position**: the last exchange the app has been given, by any route
(news, `read_session`, `catch_up`). The hub keeps it per session (a row id and a time).

- Every session tells the hub about every finished turn with a **thin event**: who sent the
  message (from `origin`), when, and how long the reply is. **No text.**
- Sessions that are watched, and turns the app started, send the **full event** as now.
- `list_sessions` shows `unheard: 3` beside a session. One number, almost no tokens.
- `read_session` with no arguments returns what is unheard (or the last exchange when nothing is).
- `catch_up` moves the position to now.

This replaces three mechanisms (the forApp filter as the only gate, the 7-day unheard store, the
"carry" list) with one, fixes incident 1 (the app learns that an unwatched session did
something, without its text leaving the computer), and fixes 4.2.5.

### 6.3 News that cannot be lost

1. **The app confirms.** Every result that carries news ends with its number:
   `news 41-43`. `wait_for_updates` takes an optional `heard` (the highest number the assistant
   has received). The hub treats news as heard only up to `heard`; if the assistant passes 40
   because the call carrying 41 to 43 failed, they come again. If `heard` is left out, the hub
   behaves as today. A small integer is easy for a model to carry.
2. **A caller that left cancels its wait.** The Worker listens to `request.signal` and to
   `notifications/cancelled`, and tells the hub to drop that waiter without touching the cursor.
3. **The transcript is the backstop.** Whatever happens to the feed, `read_session` can always
   fetch what a session said. The inbox count makes a gap visible ("Nav: 1 unheard").
4. **Old news is a pointer, not a replay.** News older than the app's last call by more than a
   set time (suggest 30 minutes) is delivered as one line per session: "Nav finished 14 turns
   while you were away, the latest 2 hours ago: catch_up or read_session." Nothing is cut; the
   content is one call away, and only if wanted.
5. **Keep-alive on long holds.** Answer the long-hold calls as an event stream with a comment
   line every 15 to 20 s (and a progress notification when the caller gave a progress token).
   Do this only after the diagnostic log shows where holds die (9.3).
6. **A diagnostic log you can read.** The hub keeps its last 200 calls in storage: tool, start,
   how long it was held, how it ended (answered, timed out, caller left, restarted). `GET
   /api/diag` with the key returns them. Incident 2 then answers itself the next time.
7. **Storage tidied by an alarm**, not on every event; reads start at the cursor instead of
   listing the whole feed.
8. **Sends are safe to repeat.** Same text to the same session within two minutes returns the
   earlier message's id instead of sending again, unless the assistant passes `again: true`.

### 6.4 Reading the transcript (`read_session`)

How the plugin reads, so that it is both exact and safe against format changes:

1. **Structure from the API**: `$.session.messages({ last: N })` gives the live chain (it already
   handles compaction and rewinds) with a `uuid` on each row.
2. **Facts from the file**: read the transcript's tail with `$.fs.read(path, { offset, length })`
   and look up each user row's `uuid` for `origin`, `isCompactSummary`, `isMeta` and the
   timestamp. If the lookup fails (the file format is not a contract), fall back to today's guess
   and say so in the result.
3. **An exchange** = one message from a person (origin `human`/`composer`, `plugin` codebridge or
   voice, `bridge`) + the final reply + the changes. Compaction rows, interrupt markers,
   notifications and peer deliveries are not exchanges; a compaction is reported as a marker
   ("the conversation was compacted here").
4. **Paging**: results stop at a character budget (suggest 20,000 by default, 120,000 at most)
   on a message boundary and return a `next` cursor. A single message larger than the budget is
   paged inside itself with an explicit "continues" marker, so it still arrives whole across
   calls and never hits the app's 150,000 limit.
5. **Search**: `find: "text"` returns the exchanges that contain it, with the matching lines
   quoted. No model.

For a **closed** session, the device agent does the same read from the file (it already parses
transcripts for names and lists), so a session can be peeked at without resuming it.

### 6.5 The briefing (`catch_up`)

- **Made only when asked.** Nothing runs at turn end.
- **Stored** in `$.store` under the session's id: the text, the row id it covers through, the
  time, and what it cost. It survives reloads and restarts.
- **Built from the new part only.** When asked and stale: one completion with no history
  (`$.model.complete`) over *the previous briefing + the exchanges since it*. The cost follows
  what is new, not how long the session is, and has no cold-cache cliff.
- **Seeded cheaply.** With no briefing yet: use the latest compaction summary if the transcript
  has one (already written, free); else one `$.model.fork` if the cache is warm (best quality for
  one cache read); else build from the last 30 exchanges and say so ("covers the last 30
  exchanges").
- **Warm or cold is measured.** Every fork's `usage` says how much the cache served. The plugin
  records the age of the last main request and what the cache did, and learns the real lifetime
  instead of assuming 5 minutes or an hour.
- **A full re-read is a choice.** `catch_up` with `depth: "full"` runs the fork whatever the
  cache state, and the result says what it cost.

Which model writes the incremental briefing is your decision (open question 1). Either way it is
no costlier than the session's own model.

### 6.6 Never waiting in silence

- **Permission prompts go to the app** in watched sessions and app-started turns, as questions
  do now: "Nav wants to run `git push origin main`. Allow?" The local dialog stays live; the
  first answer wins. Answer with the same tool as questions. Deny is the default when unclear;
  allow applies to that one call only, never a standing rule.
- **Anything else that blocks** (plan approval, a dialog the plugin cannot answer) becomes a
  news line: "Nav is waiting on something on its screen", with `show_screen` as the next step.
- **A ping to the phone** when a session finishes or asks while no call is waiting and you are
  away from the computer: `$.ui.notify` with `untilBack`. If that does not reach your phone
  (9.5), Remote Control's own push is the fallback, and costs nothing to turn on.
- **Keep the Mac awake** (`caffeinate -i`) only while a turn the app started is running.

### 6.7 Voice-shaped replies without cutting anything

Three options, yours to choose (open question 3):

- **A. As now.** The assistant relays everything in full.
- **B. Whole, in two steps.** The assistant gives the outcome and asks "want the rest?"; the rest
  is already in its context. Nothing is cut, but you decide whether to listen to all of it.
- **C. Ask Claude Code to lead with a spoken summary** on turns that came from the app: a short
  note added after the app's message (at the end of the conversation, so it does not disturb the
  prompt cache) asking for two or three plain sentences first, then the full reply. Combined with
  B, the first sentences are always the right ones to speak.

### 6.8 Safety additions

- **Link with a device secret** (4.6.1) and **revoke a computer** from the panel and by voice.
- **Rate-limit and clean up** link codes; delete expired offers.
- **Thin events** for unwatched sessions (privacy).
- **A per-session "voice may run commands" level**: off (drafts only), ask first, on. Default on
  for sessions the app started, ask first for sessions it did not. Open question 6.
- **Permission answers need the person's words.** The instructions say: never allow on your own;
  read the request out; allow only on a clear yes.
- **Logs and sockets in the private temp folder**; the key file created with mode 600.

### 6.9 Remote Control as the screen

When a session has Remote Control on, its page in the Claude mobile app shows the full transcript,
diffs and approval buttons. The bridge can say "it is long; it is open in the Code tab if you
want to read it" instead of reading 2,000 words aloud. This costs nothing to try and needs no
code beyond a line in the instructions. Whether the bridge can hand over a direct link is **not
verified**; the plugin API did not show the session's remote URL.
